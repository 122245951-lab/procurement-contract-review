# 命中项数据结构（Ops）与报告字段约定

所有审核轨道（代码硬规则 / LLM 语义）产出统一的命中对象，`render_report.py` 据此渲染交互组件。字段名即前后端契约，扩展规则时保持不变。

## 命中对象（hit）字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `rule_id` | string | 规则编码，如 `R-PAY-01`；须与 manifest 一致 |
| `track` | string | `hard`（代码）/ `llm`（语义） |
| `judge` | string | `hard_match` / `value_check` / `rule_check` / `semantic` |
| `severity` | string | `高` / `中` / `低` |
| `category` | string | 人类可读分类，如"援引失效法规""违禁表述""必备要素缺失""阈值验算" |
| `location` | string | 章节/条款定位；要件缺失可填"全文（未检出）" |
| `quote` | string | **原文逐字摘录**；要件缺失时为空串 `""`。非空时必须能在原文检索到（防幻觉） |
| `problem` | string | 问题描述（一句话说清风险） |
| `suggestion` | string | 可执行修改建议 |
| `pinned` | bool | 是否置顶（失效法规硬规则为 true） |
| `hidden` | bool | 是否隐性规则（未命中不展示，命中置顶） |
| `quote_verified` | bool | quote 是否已通过原文检索校验 |
| `need_human` | bool | （LLM 轨道）是否建议人工复核 |

## 四要素硬性要求

每条进入报告的命中必须满足：**定位 + 原文摘录（或明确"要件缺失"）+ 问题 + 建议** 四要素齐全。缺任一或 `quote` 校验失败 → 不得进入报告。

## 报告排序与呈现规则

1. `pinned=true` 置顶（失效法规）；
2. 其余按严重度 高 → 中 → 低；
3. 同严重度按 `rule_id` 稳定排序；
4. 未命中的 active 规则折叠到"已检查 N 项未发现问题"；`draft` 规则不计入正式问题也不计入未命中清单；
5. 顶部汇总：高/中/低计数、命中总数、未发现问题规则数；
6. 水印：规则包名称 + 版本 + 生效日期（可追溯"按哪版规则审的"）。

## 交互组件

- 每条卡片：严重度色条、规则编码+名称、定位、原文高亮（`<mark>`）、问题（可编辑）、建议（可编辑 + 一键复制）、接受/拒绝复选框（互斥）、状态标记。
- "导出审核意见 (Markdown)"：把命中项与未命中清单导出为 .md，附规则包版本与免责声明。
- "打印/存 PDF"：调用浏览器打印。

> 说明：BRD 中"Ops 操作指令"在 Coze/Dify 版用于前端渲染替换/高亮组件；本本地化 skill 直接由 `render_report.py` 生成等价交互 HTML，无需独立 Ops 层。若移植回 Coze，可把 hit 列表映射为 Ops 指令（高亮 span + 替换建议 + 批注）。
